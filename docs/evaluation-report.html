A correction made mid-evaluation

62.5% → 87.5%, with no new LLM calls

grading bug, not a system bug

The first eval run reported only 62.5% auto-gradable accuracy. Investigating the failures found the problem was mostly in my own grading script:

  1. Unit-scale bug. Ground truth is in AED million, but the agent sometimes correctly answers in AED thousand (e.g. "AED 5,123,259 thousand" for a 5,120.263-million ground truth — the same figure). The original matcher compared raw digits only, so a numerically-correct answer in a different unit scored as wrong. Fixed by checking the extracted number at 1×, 1000×, and 0.001× scale.
  2. A genuine ground-truth labeling error, mine. SF-04 asked for "basic EPS for Q3 2024"; I had recorded 1.10 as ground truth, which is actually the nine-month cumulative EPS on the same filing line — the correct discrete three-month figure is 0.38. The system's answer (0.38) was right; my test suite was wrong.

Both fixes were applied to the grading logic and ground truth, then re-scored from the same saved model outputs — no re-running until a passing result appeared. Reported here in full rather than only showing the corrected number.

Failure analysis

CALC-04 — gave up rather than fabricating

retrieval failure
"What was the percentage growth in FAB's full-year net profit from 2022 to 2023?"

The agent responded that the figures were "not available in the provided tool results." Not a hallucination — both FY2022 (AED 13,411.198M) and FY2023 (AED 16,405.493M) figures are in the corpus and were retrieved successfully by other questions in the same run. This question's particular search phrasing didn't surface them within the planner's iteration budget.

TEMP-01 — false "not available" after hitting the iteration cap

retrieval + iteration cap
"How did FAB's total assets change between the end of 2023 and the end of 2024?"

Claimed FY2024 data "is not yet available" — incorrect; the FY2024 filing is in the corpus and was used correctly by other questions in this same run. The trace shows it ran the full 8-iteration cap and gathered 30 citations without landing on the specific Total Assets figure, then synthesized a false negative instead of "I searched extensively but could not confidently locate this." Connects to a limitation in the Architecture Document: Total Assets lives in a segment-reporting note, not a cleanly-labeled balance sheet line, and is harder for hybrid retrieval to surface than Net Profit or EPS.

AMBIG-01 — guesses a period instead of asking

unaddressed gap
"What was FAB's net profit?" (no period specified)

Expected: ask which quarter/year, per the assignment's requirement that ambiguous queries prompt for clarification. Actual: picked the most recent period (FY2024) and answered directly. The planner's system prompt guards against fabricating figures but doesn't yet instruct it to recognize an ambiguous scope and ask before proceeding — a real, unaddressed gap, not yet fixed given time constraints.

CALC-01 — correct within tolerance, surfaced a real basis inconsistency

passed, with a caveat
"YoY change in Net Profit between Q3 2023 and Q3 2024?"

Answered 5.03% against a 4.86% ground truth — both within the 5% tolerance. The gap: the agent's Q3 2023 figure was on an "attributable to shareholders" basis while Q3 2024 was "total incl. non-controlling interests" — each individually correct from its own filing, but not on a matched basis. This is exactly the corpus-level basis inconsistency documented as a known limitation: 2022–2023 filings only state the attributable figure; 2024 filings state the total. The system has no basis-normalization step yet.

What worked well

  • Simple factual retrieval: 100% (6/6), exactly matching hand-verified ground truth once the eval script's unit bug was fixed.
  • Multi-hop reasoning: 100% (4/4, manually verified) — correctly chained temporal resolution → multiple filtered searches → calculator calls → cited synthesis, including the assignment's own flagship query type (YoY comparison with explanation). One example chained a 3-year, 2-step growth calculation correctly in a single pass.
  • Out-of-scope refusal: all 3 true out-of-scope questions (a different company, a future prediction, an unrelated topic) were correctly refused — the one failure in this bucket (AMBIG-01) is a distinct behavior (ambiguity handling) grouped in the same category.
  • Citations: 100% of retrieval-based answers cited a real source/period/page; the calculator-only and refused questions correctly had none, since no retrieval was needed.
  • Calculation tracing: every calculator call in every trace shows the exact formula and inputs used, satisfying the requirement literally.

Gemini 2.5 Flash, paid tier — finalBoth limits removed; the same query dropped from 80-150s to ~21s, and the full eval completed in minutes instead of 20-30+.

Cost and latency (measured, not estimated)

Average latency was 12.9s/query across all 23 questions on the paid tier with minimal pacing, averaging 3.17 tool calls per query. Simple factual queries averaged 11.1s; temporal comparison queries, which chain the most tool calls, averaged 23.4s. At Gemini 2.5 Flash's published pricing (~$0.30/$2.50 per M tokens), running all 23 questions cost well under $0.50 total — consistent with the Architecture Document's per-query estimate of $0.01-0.03 for a multi-hop query.
